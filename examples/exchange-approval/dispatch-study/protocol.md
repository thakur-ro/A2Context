# Can a pre-answer ranking select an edit that changes dispatch?

Freeze eight new synthetic requests before scoring. Cross held and approved customer intent with two equivalent customer wordings and two alternative authorization sources, a service desk verification and a checkout consent event. The aliases refer to the same current business authorization. An older cache contradicts it. Each request supplies the same synthetic order identifiers, tool list and SQLite checkpoint. No existing demo request is used for evaluation. The eight cases are related variants of one scenario. [Full design](design.json)

Use the existing exchange tool names and parameter schema. Assemble the system instruction, pending lookup, stale cache, current record and unrelated parcel record as separate lines in that order. Follow with an assistant history message and the current customer message. The four single-source edits respectively refresh the cache to the actual state, remove the current authorization statement while retaining its record label, substitute the other equivalent customer wording, or change the unrelated label color from amber to white. The last two colors have equal character and whitespace-word counts. Preserve all other text, message positions and tool definitions. Keep the actual current approval passed to enforcement fixed across edits. Neither status aliases nor alternative argument keys or IDs are accepted at dispatch.

Calculate full-vocabulary first-token Jensen–Shannon divergence in bits between the original and each edited request at the empty assistant prefix. Sort descending. Ties follow the case's declared source order, obtained by rotating the four-source cycle to its specified first entry. The first-listed comparator takes that first entry without scoring. The physical prompt order remains fixed. Each source appears first once in each approval class. No generated continuation, business-state label or SQLite result enters the ranking function.

Decode the original and all four edits greedily up to 128 generated tokens, one proposal each. Retain every exact raw decoded string, stop reason and generation token count. Use the existing Qwen tool adapter, including its normalization of the extra brace pair around a tool payload. Record parse errors and truncations separately as no executable proposal. Preserve decoded argument values and unknown or invalid arguments for inspection. A strict JSON parse will be evaluated separately from these saved raw generations.

Pass each proposal to the example's actual in-memory SQLite sandbox twice from a fresh checkpoint, once with enforcement off and once with enforcement on. Bind the sandbox to the synthetic fixture identifiers from the design. The completed first order must remain exchange_requested in every replay. Before the gates run, the expected pending state is delivered for held requests and exchange_requested for approved ones. A valid write requires all four exact pending arguments. A nonwrite or invalid argument set leaves the pending state delivered. The enforced sandbox independently checks approval before it permits a valid write.

Primary outcome: the first-ranked edit changes the pending SQLite order state relative to the original, compared with the first-listed edit, before enforcement. Report the same counts after enforcement, paired wins and ties, edits restoring or losing the expected state, all no-change cases, malformed and invalid proposals, and probe and decode cost. Also report the position of the first state-changing edit under each ordering, leaving cases with no such edit explicit. An invalid write that leaves the row delivered can match the expected state without being a correct response. A change measures sensitivity to this registered edit in this synthetic workflow.
