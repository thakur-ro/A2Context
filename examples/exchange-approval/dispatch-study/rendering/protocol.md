# Does the native tool renderer change a validated exchange call?

All eight responses in the preceding exchange study finished as ordinary text. Compare all eight captured inputs, the stale and refreshed consent versions of four synthetic orders. The previous baseline responses are known. The eight alternate responses have not been generated. This repeated-request transfer check does not introduce new orders or independent observations. [Parent study](../prospective/README.md)

Use two published tool renderers with the same XML tool-call wire format. The reference is the Qwen-Agent 0.0.34 Nous preprocessor followed by plain chat tokenization. The variant supplies the workflow messages and the identical ordered effective schemas to the native tools branch of the Qwen2.5 tokenizer. Qwen-Agent omits the application's additionalProperties field in its registered tool declarations. Preserve that same omission in both renderings. The framework's alternative qwen configuration uses a different response grammar and corresponding parser. The tokenizer implementation gives a renderer-only comparison while keeping the Nous parser.

Before decoding, re-render and hash both complete prompts for all eight inputs. Require byte equality except for one additional opening and one additional closing brace around the example tool-call JSON in the tokenizer template. The workflow messages, consent status, tool names, order, descriptions and schema field values stay identical. Record input token count and digest for each renderer. If these checks fail, stop before generation. [Render manifest](design.json) · [Renderer checks](renderers.py)

Run the pinned Qwen2.5-0.5B-Instruct CPU float32 checkpoint with four threads, greedy decoding and 128 output tokens. Run both renderers anew for each input, in frozen case/consent order, reference first. Send each raw output unchanged through the Qwen-Agent 0.0.34 Nous parser, registered tool validator and the same isolated two-order SQLite entry point. Execute both gate policies with identical output. No retries. Preserve raw output, stop reason, output token IDs, parser-emitted name and arguments, validated choice, and database before and after states. Verify the reference outcome and completion tokens against the previous study. Repeat all alternate generations in a separate process. Recheck hand-built tool-call controls using the existing parser and SQLite code.

Compare the parser-emitted expected name, validator acceptance, exact expected name plus arguments, and expected entire database state separately. Count state restorations, losses and unchanged cases by gate for each pair. Treat truncated responses as unscorable for action-effect comparisons. Report changes to raw completed text separately from tool or database changes. Report first-run and repeat calls, tokens and elapsed decoding time. Each case retains its pre-existing target, fixed before the earlier study. No externally dispatched operations or paid inference.
