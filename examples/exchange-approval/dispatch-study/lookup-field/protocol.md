# Does changing a payment lookup value change the generated argument?

Take the repaired-cache input from each of the four known exchange orders. Reuse the native Nous rendering, pinned Qwen checkpoint, four CPU threads, greedy decoding and caller-supplied tool opener from the preceding study. All four original proposals and their outcomes are already known. This is a prospective intervention on new field values in an established forced response branch. [Preceding experiment](../prefill-tool/README.md)

Freeze three inputs per order in order. Original keeps the full request. Lookup replaces only the final decimal digit of the payment_method_id in the system order lookup with its successor modulo ten. The entire replacement identifier must be absent elsewhere. Punctuation changes only the period at the end of the first user message to an exclamation point. That earlier message names the products; it contains no consent or payment reference. Require each edit to change exactly one ASCII byte and one token without shifting any token index or touching any other byte. This punctuation control matches edit size and varies a different message, position and token class. It does not test all alternative perturbations at the target position. Save portable pending envelopes with a payment-lookup source and an expected digest pinned from the original application design. The identical digest for all three arms of an order stays outside the model input. Record model-boundary source pointers and UTF-8 byte ranges, full-field token coverage, actual changed token IDs/positions, original field digest, rendered text and token digests before inference. Keep the same two-token provided assistant opener and 126 remaining generation tokens. Repeat the original fresh, then run the lookup and punctuation edits. Use Qwen-Agent’s actual Nous parser and native registration/argument validator. Verify the exact reconstructed suffix plus supplied prefix before calling tools. Keep the original four required IDs, order rows, gate settings and customer authorization immutable for all three arms. New payment values are hypothetical and confer no authority. The existing sandbox rejects wrong arguments before checking approval. Record that rejection separately from a blocked unauthorized exchange, a completed write and a native schema rejection. Check the same raw output under both policies. Check hand-written valid and modified-payment calls against the same native validator and original database. Never dispatch externally.

For each completed trial, record tool name, schema validity, whether the generated payment value equals the authentic value, the substitute, another value or is absent, whether the tool and three other fields match the original generated write, exact agreement with the application's expected tool and arguments, and both full two-order state receipts. Compare targeted and control edits with the same original, including state restorations, losses, unchanged states and unscorable pairs by gate. An incomplete generation is unscorable and has no tool callback. Retain every arm and state what fraction of the four paired comparisons show a generated value changing to match the substituted lookup. Repeat all eight edited generations in an independent process, with exact suffix/receipt checks. Record costs and reference the prior measured original output. No tuning after the first alternate output.
