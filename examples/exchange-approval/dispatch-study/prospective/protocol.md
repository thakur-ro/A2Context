# Can refreshing stale consent repair an exchange workflow?

The earlier exchange walkthrough exposed a cache authorizing a write after the customer put the order on hold. The native Qwen-Agent replay also showed that different argument parsers can change the final order. Before generating any answers, select one repair for all four new orders. Refresh the pending exchange’s cached consent from its latest application-recorded customer event. Each baseline has the opposite cached value. In production this requires a reliable consent event and a way to refresh that record. The application supplied the event in this experiment. [Earlier conflict](../../../../docs/demo.md) · [Framework findings](../framework/README.md)

Use the four cases in design order. They have eight fresh order IDs, four sets of argument values, four product pairs, four latest messages and balanced hold/approve targets. Each model sees the same transcript and tool definitions across the pair. Only the cached status phrase changes, with the same expected tool, exact arguments and two-order database state in both arms. The function that builds the template and exact targets is frozen with the cases. The previous order always stays exchange_requested. An approved pending order should receive the exchange tool with all four lookup IDs exactly and finish exchange_requested. A held order should receive message with content exactly “Exchange paused.” and finish delivered. Free text is reported separately even when the database stays as expected. [Cases](design.json) · [Request and target definitions](scenarios.py)

Use Qwen-Agent 0.0.34 FnCallAgent and its native Nous instruction transformation, function parser and tool validator. Record the exact application request including tools, the actual framework-assembled model messages, and the UTF-8 byte ranges of the cache and latest customer instruction in that boundary. Record a portable pending-request envelope at that boundary. Tool schemas are embedded in the framework’s model messages. Render once with the frozen Qwen tokenizer and no second tool-schema injection. Record the rendered string and tokens’ SHA-256, token count, output IDs, raw completion, end reason and native parser output. Use local Qwen2.5-0.5B-Instruct revision eaa56b5 (the full revision and snapshot hashes from the existing CPU study), float32, greedy, four threads, 128 new tokens. No retries or remote services.

For each arm, start a fresh two-order in-memory SQLite sandbox and collect the ungated and enforced results for that same generated string. Stop after the first tool callback or completed text. A completion at the token limit is unscorable and dispatches nothing. Preserve the unchanged checkpoint separately from a verified correct proposal. Save every arm. Report exact tool/argument agreement, expected state per policy and paired states restored, lost or unchanged. Compare direct effects only within the four paired cases. This deliberately enriched sample cannot estimate how often stale caches occur in deployed workflows.

Repeat the four baselines in a fresh Python process and compare prompt, output, parser and SQLite receipts, excluding wall-clock time. Replay all eight saved outputs through the actual framework and database, recheck their fragments and renderings, and report model calls, tokens and elapsed decoding time separately for the repeat. A repair can leave or worsen an original outcome. The preselected edit stays fixed regardless of those results.
