# Can a discovery result change the database agent's next action?

All five Collector questions ended in a text reply without a tool proposal. The captured catalog offered a no-argument function for listing tables. Test whether the model needed information about the connected resource before it would continue. Use all five saved opening requests from the frozen Collector database pilot. This is development evidence on a known failure.

For each question, preserve its wording, tool catalog and sampling conditions across four arms. Send the original request twice. In the third arm append an assistant invocation of `list_tables` and its actual result, obtained once by running the installed LlamaIndex tool on the read-only pilot database. In the fourth arm use the same invocation and substitute two unrelated English table names, `shelves` and `volumes`, for `changes` and `commits`. Require the same result length, punctuation and message structure. This controls for the presence of tool history. The substituted inventory exists only in the experiment.

Use the original local LFM2.5-1.2B-Instruct runner, temperature 0.5, a 512-token limit and seeds 11, 29 and 47. Randomize all four arms within each question and seed. Count whether the **next** assistant reply proposes an advertised tool. A more specific endpoint counts a request for one or more actual table schemas or a read-only query that prepares against the real database and reads at least one of its two tables. An unconstrained schema request, repeated table listing and unrecognized names fall outside this specific endpoint. Retain every proposal, argument, HTTP failure and empty reply. Prepare queries with SQLite EXPLAIN and a read-only authorizer. The runner never dispatches a generated proposal.

Report raw counts for both outcomes and paired gains and losses against each control. If the table-specific result moves, the experiment supports testing an application-provided discovery step on this setup. A proposal alone cannot establish that the user would receive a correct answer. Automatic capture cannot supply a missing resource inventory until the application makes one observable.
