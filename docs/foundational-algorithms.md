# Diagnose an LLM workflow from ordinary usage

A team should be able to deploy the sidecar in development or production, use its application normally, and receive a useful recommendation without preparing test cases, expected answers or a judge prompt. The first milestone is the time it takes a team to discover a real problem this way. The source-edit experiments below are an optional way to investigate a finding.

## What counts as context

Follow what the application sends at each model call. This can include system and developer instructions, conversation history, tool definitions and results, retrieved articles, memory, skills, MCP resources, injected guardrails, images or other input parts. Preserve producer-defined types, source revisions, order and request locations when available. A tool registered on a server may never reach a model. A timeout, permission denial or parser exception belongs to the execution record and only becomes model context if a later request contains it. Hosted integrations can establish what was sent. Exact model input tokens require an instrumented runtime. Mark redacted, unsupported and uncaptured parts explicitly.

## From a stalled run to a recommendation

Consider a tool that successfully returns a document ID. The agent asks for the ID again, then stops. The useful question is where progress broke. Link the tool call to its result by invocation ID and inspect the next model request. If the complete request lacks the result, show both locations and suggest checking how the application appends tool results. If the request includes the ID, that explanation loses support. If the exporter omitted message bodies, report the capture gap. If the workflow recorded an exception before it made another request, show the exception and its call site. An open trace with no next event could still be waiting for a person or a late span.

The proposed background worker would do the following:

1. Process new spans incrementally. Use the existing bounded queue and SQLite indexes to join requests, tool calls, results and subsequent turns. Revisit a finding when late evidence arrives. Exact joins establish events cheaply.
2. Look for places where progress diverged. Use observed corrections, rejected tool proposals, exhausted retries, explicit failures and normal completions to shortlist comparable runs. Keep successful recoveries as comparison cases. A repeated action alone is weak evidence. A single well-documented error can be useful on day one in development.
3. For ambiguous cases, optionally compare a bounded sample of unsuccessful and successful runs from the same workflow version and task type. A model may propose an explanation from the cited snippets. Check its references, show alternative explanations and identify one concrete next action. Group recurring cases under the same finding. Refresh it when new evidence changes the advice. The inference request never waits for this analysis.
4. Publish what happened, the affected scope, the source or runtime event to inspect, and how certain the diagnosis is. If the evidence cannot distinguish explanations, say what observation would resolve them. A sandbox replay is optional when the question is whether a source actually changed the odds of an answer or tool call.

The sidecar already captures supported spans, indexes source references and groups findings. Cross-workflow stall diagnosis and ranking recommendations by confirmed usefulness are proposed work. In a saved study of 2,954 held-out failure traces, the first explicit error pointed to the injected mistake in only 68 of the 233 traces it flagged. An error message was often a downstream symptom. [Failure localization study](recommendation-loop.md#seventh-pass-check-when-a-failure-becomes-visible)

## How we will measure the recommendations

| Question | Pilot measure |
| --- | --- |
| Did it help the engineer? | For the first five distinct suggestions per workflow, record how many the engineer confirms identified a concrete issue worth acting on. Show useful, dismissed and unreviewed counts and the number actually shown. Record whether the proposed action helped separately. |
| What did it miss or misidentify? | Independently review a sample of flagged and quiet conversations. Record missed incidents, incorrect source or step, and cases with insufficient capture. Sample successes too. Weight sampled strata by their prevalence when estimating coverage. |
| How much noise did it create? | Count dismissed and duplicate notifications per 100 observed conversations, with the review response rate. Group multiple symptoms from the same incident. Silence and clicks carry no usefulness label. |
| How quickly did it help? | Measure installation to first surfaced recommendation later confirmed useful. Include deployments still waiting at the end of the pilot. Also report p50 and p95 from ingestion of the first sufficient evidence to visible finding, separately from engineer review time. |
| What did it cost the workflow? | Measure change in inference p95 with the same traffic and exporter, queue drops and processing lag, peak memory, and analysis tokens or spend per 1,000 calls. Break down dev and production. Keep the default path free of model calls. |

In the first pilot, start from empty state on a previously unseen tool-using workflow and a retrieval workflow. Use normal usage, then have engineers review a small sample after suggestions appear. Compare the proposed recommender with the current feed on the same traffic at the same notification and compute budgets. Report by workflow, including those with zero useful findings. Promote the new ranking only when it improves confirmed usefulness without increasing reviewer burden or exceeding the deployment's agreed latency and cost limits. This review measures A2Context and imposes no eval setup on the team using it.

The frozen feed surfaced zero suggestions on both public pilot workflows. A follow-up found a tool description that named an absent tool. Correcting the description increased first-step tool use on zero paired trials and decreased it on two. Future recommenders can use these sessions for development. Another prospective test needs fresh workflows. [Pilot and intervention results](../examples/ordinary-usage/README.md)

## A score for the monitored workflow

**Proposed measure.** Report the percentage of assessable runs that passed a named set of operational checks. Start with one capability, such as tool handoffs. An example check asks whether a tool result designated for delivery appears in the next model request with its invocation ID. Apply that check only to runs with a handoff due. Intentional termination, an expected human wait and legitimate result transformations need explicit treatment in the check definition. Publish the check set and version. Teams can use the built-in checks without supplying test cases or grading answers.

For one workflow version, environment and time window, count distinct eligible runs. Use the underlying evidence for recommendations before ranking, suppression or display. Each run receives exactly one status.

| Count | Meaning |
| --- | --- |
| $B$ | Evidence establishes at least one monitored incident. Three recommendations about the same run still count once. |
| $C$ | At least one check applied, and every applicable check completed with a pass. |
| $U$ | The available evidence leaves the status unresolved. For example, the next request was only partially captured. |

With $N=B+C+U$, the **monitored pass rate** is $100C/(B+C)$ and **assessment coverage** is $100(B+C)/N$. Report both with the counts. When $B+C=0$, show “insufficient evidence.” Use an independent application run count when available to quantify runs missing from telemetry altogether. Otherwise limit the claim to recorded eligible runs. The event-ratio construction follows established service-level indicator practice. [Google SRE Workbook](https://sre.google/workbook/implementing-slos/)

For illustration, 882 passes, 18 affected runs and 100 unresolved runs give a 98% pass rate at 90% coverage. If every unresolved run failed, 88.2% of the eligible cohort passed. If every unresolved run passed, 98.2% passed. These bounds, $[100C/N,\;100(C+U)/N]$, reflect missing evidence even if missingness is related to failure. They assume resolved classifications are correct. They describe this cohort and supply no statistical guarantee about future traffic. [Horowitz and Manski on incomplete data](https://www.sciencedirect.com/science/article/pii/S030440760500062X)

**Available check.** Ask **Show the tool reference score** in the interview or query `GET /api/sidecar/tool-reference-score`. Version 1 checks a narrower property than delivery: each tool-role result in a recorded chat request must have a nonempty ID matching exactly one preceding assistant tool call in that request. It measures distinct normalized traces in the selected scope and trace-start window. The interview gives counts, missing-data bounds, and up to five affected traces with the exact message position. It can reveal a broken reference in an assembled history. Establishing that a result never arrived, that its payload was correct, or that a task succeeded requires other evidence. A trace with known tool-result input but incomplete evidence can be unresolved. The API reports traces of unknown applicability and fully inspected traces outside the check separately from the eligible denominator.

**Validation before publication.** Independently review a random sample within each status, retain sampling probabilities, and estimate false alarms and missed incidents with their denominators. Check agreement on ambiguous cases. Compare periods under the same check set and comparable traffic and run lengths. Report individual check rates alongside the aggregate so frequent low-impact issues cannot conceal rare serious failures. A hypothesis about model influence stays outside the incident count until the operational check's evidence criterion is met.

Our saved failure-localization cohort illustrates the risk of treating silence as a pass. All 2,954 held-out traces contained an injected mistake. The explicit-error signal fired on 233, leaving 2,721 (92.1%) silent. The fraction is exact for that cohort and detector. Calling it agent health would reverse its meaning. A semantic classifier can suggest conflicting excerpts. | Preserve scope and precedence when screening pairs. Challenge the shortlist with exceptions, quotations, superseded rules and harmless repeats. Score precision and coverage on individually labeled pairs. Give both excerpts for every proposed conflict. |
| At a prediction position | With a scorer, edit one anchored source and compare next-token distributions or a named candidate margin at the same prefix. With an instrumented model, patch a specified activation and retain its position and controls. | Compare cheap selectors with full leave-one-source-out scoring. Report the edit, token position, effect and units. Mark positions with no measurement. For suspected redundancy, test both single edits and their joint edit against the same baseline. |

## How to read an effect

- **Before the first output token**, one available score is the Jensen–Shannon divergence in bits between the original and edited next-token distributions. Later positions hold the earlier output fixed. A high score makes the edit a candidate for free generation. The later answer and tool outcome remain open. Our prefill selector adapts ARC-JSD. [ARC-JSD](https://arxiv.org/abs/2505.16415v5)
- **During generation**, compare the log probability of the same output token under the original and edited source at the same prefix. Preserve the sign, model revision, source edit and position. Layer interventions also require aligned positions, clean-to-clean and donor controls. ContextCite and AttriBoT are related attribution baselines. [ContextCite](https://proceedings.neurips.cc/paper_files/paper/2024/hash/adbea136219b64db96a9941e4249a857-Abstract-Conference.html) · [AttriBoT](https://proceedings.iclr.cc/paper_files/paper/2025/hash/2aab664e0d1656e8b56c74f868e1ea69-Abstract-Conference.html) · [Activation patching guide](https://arxiv.org/abs/2404.15255)
- **For a workflow outcome**, define success before running the edit. Estimate the edited success rate minus the original rate. For a pair of sources, the interaction on that same scale is the joint effect minus the two single effects. Report raw counts for each arm. Group effects only when outcome, model, edit, prefix and runner conditions are comparable. Keep “untested” distinct from a measured zero.

## Optional study of source influence

**Hypothesis.** Given one source edit per request, a pre-answer selector can identify more edits that change the declared outcome than the best simple selector at comparable cost. Every selector also pays for the same baseline and no-op control. Start with deterministic decoding and a resettable sandbox. A later stochastic replication needs repeated trials per arm. Recommending an edit for deployment also requires evidence that it improves the intended outcome and preserves valid behavior.

1. **Reproduce the starting line.** Run `make check-qa check-dispatch-study` from the repository root. From the 17 QA cases with complete paired answers, the highest-divergence edit changed 14 answers, gained one reference match and lost three. The first-passage edit changed 11 answers and preserved all three initial matches. Three more questions had incomplete pairs. On five airline checkpoints the divergence selector always chose the last customer message, which a zero-probe rule also chose. Use both cohorts for development from now on. [QA measurements](../examples/public-qa/holdout-results.json) · [Paired comparison](../examples/public-qa/holdout.md) · [Airline measurements and capture limits](../examples/airline-transfer/README.md)
2. **Freeze a fresh comparison.** Select new tasks from one retrieval workflow and one tool workflow before inspecting outcomes. Group shared questions, conversations, templates and task variants within one split. Publish the manifests, model and parser revisions, source boundaries, seeds, edit rules, outcome predicates and compute ceilings. Include successful and failed outcomes in each workflow. Hold out an entire workflow family for a transfer check using the frozen instructions, edit operations and ranking method. Only the adapter and outcome evaluator may vary by workflow. Historical traces with no reproducible request or outcome can evaluate retrieval and recurrence only.
3. **Give each selector the same opportunity.** Compare first or last eligible source, lexical relevance (BM25), scope-matched declared rules, prefill divergence and one source edit selected by a model. The model may see only the current task and inputs for this prospective test. It cites a source, proposes one isolated edit and predicts which outcome will change. Count its proposal tokens against the budget. Pick the strongest simple comparator on development data. Apply the same candidate set and replay allowance to each selector. Count every scoring pass, generated token and sandbox run. Publish yield at equal total compute as well as at one replay. Predefine ties and abstention. Match replacement length where possible. For stochastic runners, interleave arms with the same sampling settings.
4. **Decide using paired outcomes.** The primary yield is the share of all eligible requests for which the chosen edit flips the declared outcome and a no-op preserves it. An abstention or incomplete arm contributes no verified hit. Report these counts separately, alongside gains and losses in task success. Estimate paired differences and 95% intervals clustered by independent task. Use development variance to choose the held-out size before opening labels. Promote a selector only if the interval's lower bound for improvement exceeds zero at the stated budget in both workloads. Otherwise keep the baseline and publish the misses. Test inference p95, queue drops and peak memory under the sidecar's provisional 1 vCPU and 512 MiB budget. [Existing load test](validation.md#constrained-overload)

| Milestone | Deliverable | Decision |
| --- | --- | --- |
| 1. Offline baseline | One paired table per workflow with the selected source, evaluation cost, coverage, outcome and evidence IDs. Audit both wins and losses on development cases. | Freeze the protocol before any fresh held-out scoring. Existing reports can be rescored locally without paid calls. |
| 2. Prospective selection | Run the frozen comparison on pending requests. Hide the recorded continuation, later tool states and evaluation labels from the selector. | Publish all arms and misses. Use the better-supported selector under the measured budget. |
| 3. Recurring recommendations | Group by source revision and test conditions. Show affected conversations over eligible captured conversations and report missing identities separately. Replay the chosen intervention on a fresh case. | Compare top-five actionability and coverage against the current feed on unseen workflows.
